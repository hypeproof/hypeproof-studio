## Second core batch: the persist:hp-safe session as a Studio core patch, and the extension-owned saved allowlist (2026-11-05)

Jay, 2026-11-05: port the `feat/306-hp-safe-session` patch into `scripts/patches/core/` (not a `vscodium-base` bump) together with the extension-owned saved allowlist, behind a default-off flag until a real-device check. This replaces the 2026-11-04 plan to land the patch through a deliberate submodule bump.
- Port, not bump: `scripts/patches/core/hps-safe-session.patch` is the fork's single patch (`patches/62-hp-safe-session.patch`, fork commits 6384b04 and 054654d), which applies to the pinned VS Code 1.116 files (blob ids match the fork patch's index lines); the pristine copies are in `scripts/patches/core/upstream/`. `stage-core-patches.sh` stages it as `99-hps-safe-session.patch`. Because `scripts/patches/core/` is a mac base-key input, the next mac release rebuilds the base once. Confirmed by Jay: yes (2026-11-05).
- Default off: the view uses the hardened session only while the new core setting `hypeproof.browser.hardenedSessionEnabled` (default false) is true AND the extension marks the seat with `hypeproof.browser.safeSession`. The extension never writes the new setting; it is turned on by hand on a real device for the check, and its default changes in a later PR. Confirmed by Jay: yes (2026-11-05).
- Changes to the fork patch (agent-selected; (a) and (b) narrow, (c) aligns the grammar and also admits `*.`/`.` prefixed, mixed-case and trailing-dot forms of listed hosts plus `[::1]`): (a) the three settings are application-scoped, so a workspace or folder `settings.json` (which the coach can write) cannot turn the session off or widen the list; (b) a `webRequest.onBeforeRequest` filter on the safe session cancels main-frame loads outside the allowlist, because `will-navigate` misses loads the main process starts (address bar, `loadURL`, CDP `Page.navigate`); (c) the URL matcher follows the extension's `hostAllowed` grammar (trimmed, case-insensitive, `*.`/`.` prefixes, trailing-dot hosts, `[::1]` local, malformed entries admit nothing, non-web schemes refused). Sub-frames are not filtered (the fork's scope; an allowed page may embed media).
- Saved allowlist: on every served profile the extension saves `{ seat, minor, safeSession, allowlist }` in its own `globalState` (`hypeproofChat.savedLinkSafety`), not in settings.json, which the learner and workspace settings files can edit. Seat = a one-way key of the token's cohort (`c`), else of the credential, so a renewed token for the same class keeps it. Without a loaded profile (first load, refetch, token expiry) the copy for this seat decides the link route exactly as its profile did; another seat's copy is never used and is removed on the next token change or `invalidateProfile`; sign-out removes it.
- Flag for the saved allowlist (agent-selected): the existing safe-link enforcement (`safeLinkEnforced`, `hypeproofChat.safeLinkAllowlistEnabled` default true as the support override), not the new default-off core flag. The copy is the same served list Jay turned on for minor cohorts on 2026-11-04 and only applies where that block was already on, so it closes the loading gap without a new policy. Confirmed by Jay: no.
- Failed fetch: `applyBrowserSafety(null)` no longer writes `safeSession: false` / `[]`. Once the keys are registered, that write would have turned a minor's persisted fallback into the adult path during an outage.
- Not in this batch: Korean labels for the three core settings (Korean bundles for built-in pieces: later, Jay 2026-11-05); a real-device check of the hardened session; turning `hardenedSessionEnabled` on.
- Before `hardenedSessionEnabled` is turned on (independent verifier, 2026-11-05): the upstream context-menu item "Open Link in External Browser" still opens the system browser from a safe-session tab; tabs created over CDP (`createTarget`) or opened before `safeSession` flips do not take the hardened session, and an allowlist change reaches only views created after it. A profile fetch that finishes during a sign-out can write the copy once more; it is never applied to another seat and is removed on the next token change. Account tokens carry no cohort claim, so their copy is keyed on the credential and lasts until it rotates.
