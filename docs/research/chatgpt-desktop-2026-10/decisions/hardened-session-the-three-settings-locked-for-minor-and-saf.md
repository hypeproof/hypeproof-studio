## Hardened session: the three settings locked for minor and safe seats (2026-11-07)

Jay, 2026-11-07: before the flag is turned on, a learner must not be able to change `hypeproof.browser.hardenedSessionEnabled`, `safeSession` or `safeAllowlist` (the #3559 verifier noted all three are editable in user settings).
- Where the effective value comes from (agent-selected): a lock the extension saves from each served profile in its own `globalState` (`hypeproofChat.browserSettingsLock`), which only the extension host writes. The core patch reads it directly (`hpBrowserSettingsLock`: storage key `hypeproof.hypeproof-chat`, this profile's copy, else the default profile's), so the value pushed to the main process is right before the extension activates, with the extension disabled and in a new VS Code profile. Rejected: an internal command the extension calls (a learner keybinding can call any command id with arguments) and a settings-only re-assert (the main process would follow the learner's value until the extension writes it back).
- Settings can only tighten (agent-selected): while a lock exists, a settings `true` still counts and the lock's `true` wins over a settings `false`; the allowlist is always the served one. A tester can turn the flag on for a minor seat in user settings for the real-device check without a Service change; a learner cannot turn anything off.
- How the flag is turned on (agent-selected, reversible): the served `browser_session.hardened: true` per cohort, or a later change of the registered default. Nothing serves it yet, so the flag stays off. Turning it on for a cohort is a profile change and needs Jay.
- Lifetime (agent-selected, fail closed): an adult profile removes the lock; sign-out and a failed fetch keep it. On a shared Mac the browser stays hardened after a minor signs out until another seat's profile is served. A stale copy in the default profile after a seat change made in another VS Code profile also keeps it, until the extension runs in the default profile.
- Support override (agent-selected): server-side only. An operator changes the cohort's served profile; the next profile load replaces the lock and the extension rewrites the settings. Rejected for now: a machine policy (learners commonly administer their own Macs, and VS Code policy registration needs build-time policy export work) and a CLI flag or environment variable (learner-reachable).
- Settings-file ping-pong (independent verifier): two windows in different VS Code profiles with different locks would rewrite the shared `safeAllowlist` back and forth; only `safeAllowlist` is throttled (the booleans only ever go to `true`, so they cannot ping-pong): a list a window wrote less than 5 s ago is not rewritten at once and is checked again after the 5 s (agent-selected). The core patch enforces each window's lock, and the extension's chat-link fallback (no profile, no saved copy) now reads the lock before settings.json, so the delay changes only what settings.json shows for up to 5 s (second verifier pass: a throttled `safeSession: false` had reached that fallback).
- Full TypeScript check (closes the 2026-11-07 condition above): on the Ubuntu worker, `tsc --noEmit` of the pinned 1.116 tree with the patch applied to the pristine browserView files reports the same 71 pre-existing `lib.dom.d.ts` errors as without it and with the previous patch.
