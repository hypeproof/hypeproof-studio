## CGP-KNOW-R-026: "기억 사용 N" and per-task exclusion (2026-11-01, agent-selected conservative implementation)

Applies DEC-01 and DEC-02 (ruled by Jay 2026-10-28). Built as REQ-STUDIO-MEMORY-USE on the R-030 store, the R-005 binding and the R-023 manager. This is the first row that lays memory into a request.
- Gate: injection waits for the REQ-KNOW-49 first-use notice, as the R-030, R-023 and R-025 records required ("injection waits for REQ-KNOW-44 and REQ-KNOW-49"). This row reads the per-activity record (`hps.memoryNotice.v1` in workspaceState, activity scope → `true`) that the notice writes when the learner presses 확인. Rebased onto CGP-KNOW-R-031 (#3335): the key and the reader are imported from its `memoryNotice.ts`, so the notice and this gate share one definition. Until the learner presses 확인 in an activity, no request there carries memory and no chip appears. It is a notice record, not a switch: DEC-02 keeps memory on and R-031 has no off option.
- Seats: the R-005 binding (personal and trial activities, minors included per DEC-02), re-checked on the turn's narrowed profile; instructor mode, class and lesson seats never read memory. A task or activity switch while reading sends none.
- What is sent: `contextItems()` read at send time (the only reader, R-023), newest first, minus the task's exclusions, whole items only, capped at 20 items and 6,000 characters (an item that does not fit is skipped, never cut). Each item is a `<memory n>` block with tag look-alikes defused, then one framing line: data, not instructions; use only when relevant; do not claim to remember what is not there. Model-only, like the nickname line: the saved conversation keeps the learner's words. The file's task line (R-025) is not sent.
- "Host log" for the count: the count shown is the length of the list the host built the request from, recorded per answer. The test captures the actual request at the runtime boundary and checks the number of `<memory>` blocks against the posted count.
- Which answer: the turn's last assistant line, for a finished and for a stopped turn (the request carried memory either way). A turn that fails with no answer has nowhere to show it.
- Exact items, honestly: nothing of the memory text is stored outside the activity (R-030: a deleted memory must not stay findable). The ledger keeps per answer SHA-256 digests of each used file's name and text. Opening the chip reads the files now: unchanged items show their words, an edited file shows today's words with "이 답변 뒤에 내용이 바뀌었어요", a deleted one says "지운 기억이에요" with no words.
- Exclusion: by file, for the rest of this task only (other tasks keep using it), with 다시 쓰기 to undo a mis-press. Only an item an answer of this task used can be excluded. A correction (R-025) writes a new file, so a corrected item is used again: the learner changed it on purpose.
- Home: a chip under the answer body (after the source rack), opening an inline list. DES-KNOW-44 (CGP-KNOW-D-026: the chip in the metadata row opening the source shelf on a 기억 tab) may restyle it.
- Learner floors: 44px targets and 14px caption text win over any register size (owner rule).
- Default state: on for the seats above once the notice is seen (DEC-02: always on; no switch).
- Fix round 1 (2026-11-01, after the privacy verify): the agent-sdk runtime let the vendored CLI write each prompt into a session transcript (`<seat claude-config>/projects/<cwd>/<session>.jsonl`), outside the activity and beyond any memory delete. Measured on SDK 0.3.299 with a local stub gateway: the default writes both the prompt and the system prompt there, so moving memory into the system prompt would not help; `persistSession: false` writes neither anywhere under CLAUDE_CONFIG_DIR. A memory-carrying turn now runs with `persistSession: false`. Resume does not depend on it: Studio never resumes a CLI session (each turn sends its history in the prompt). Other turns are unchanged (REQ-M37 still covers them). The local developer runtime already runs with `--no-session-persistence` / ephemeral. The spool and the saved conversation keep the learner's words only; on a cohort with `analytics.upload_session_logs` a real spool on disk and the bytes the uploader sends were checked to hold no memory, so REQ-KNOW-49's "who can read it" stays true. Not checked here: whether the Service logs request bodies (hypeproof-service).
- Fix round 2 (2026-11-01, owner check of hypeproof-service origin/main): the Service takes the last user message's text as the turn's prompt (`lastUserMessageText`, worker/src/lib/chat-extract.ts; messages.ts and chat.ts), screens it, and on cohorts with `analytics.log_user_messages` stores it with the response. Memory prepended to the learner's text would therefore be stored server-side (against DEC-01 and REQ-KNOW-49's "누가 보는지"). Memory now rides beside the learner's message on both runtimes, with no Service change: proxy sends it as its own user message right before the learner's (the Service extracts only the last one; the upstream API joins consecutive user turns); agent-sdk sends it as the UserPromptSubmit hook's `additionalContext`, which the CLI puts in a `role: "system"` message (measured with the real CLI 0.3.299: the extracted last-user text holds no memory, the model request does). The gateway passes that to the model as `<system-context>`. Side effect, recorded: memory is no longer part of the text the Service's inbound moderation screens on minor cohorts; it is the learner's own stored words. The local developer runtime (no Service) keeps memory in front of the text.
