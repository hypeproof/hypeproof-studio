# Agent PR preparation

Use the repository's `scripts/hype-pr/pr.py` entrypoint. It delegates to the canonical
Harness checkout, found as a sibling of the main consumer checkout or through
`HYPEPROOF_HARNESS`. If missing, clone `hypeproof/hypeproof-harness` into that sibling
location (or use an existing checkout via the environment variable). The sibling
checkout is only read and fetched, never switched or fast-forwarded: the engine runs
from a launcher-owned detached worktree at `origin/main`
(`~/.cache/hypeproof/harness-engine`, override with `HYPEPROOF_ENGINE_DIR`), so a
session developing Harness in that checkout keeps its branch. `HYPEPROOF_HARNESS=<path>`
only says where the canonical checkout is; the engine is still made and refreshed from
it. Set `HYPEPROOF_HARNESS_PIN=1` only to run the canonical checkout itself as it is
(no fetch, no engine), e.g. to test unmerged Harness changes. If the entrypoint says
the engine has local changes, move them out and remove that worktree; never discard
them. Preserve existing work. Python 3.11+,
PyYAML are required. Local execution uses authenticated `gh`; Work can use the
connected GitHub tools through the explicit host transport in
`docs/HYPE-PR.ko.md` → `Work GitHub transport`. Both paths execute the same
inspect/assessment/prepare/create guards. Do not copy policy or the impact engine
into consumers. Keep operations scoped to the requested HypeProof repository.

## At development start

Read the repository instructions and relevant canon, then its `config/traceability.json`.
Before creating the task branch, reuse or create an open issue in the target repository
whose scope and acceptance result match this PR-sized vertical change. An Epic is a
parent product outcome, not the PR close target. Record the Epic as context or parent
and close the scoped work issue. The guard verifies objective GitHub properties; you
and the coordinator remain responsible for judging semantic scope fit.
Find the existing Intent, REQ and test nodes for the requested change. Inspect the
actual documents before choosing parents. New criteria need a stable ID, correct
stage, an agreed domain owner and parent links; the PR author is not automatically
the owner. Extend the consumer manifest in the same branch when needed. Preserve
existing unrelated ownership/mapping debt; create follow-up work when a domain
judgment is missing rather than inventing authority or rewriting the philosophy.

`inspect` can show committed changes during development. Dirty/no-diff results are
advisory then; they must be resolved before final preparation. It does not inspect
uncommitted text. Read working changes directly when developing.

## Before creating a PR

1. Complete the requested change and appropriate validation. Commit it on its task
   branch, fetch the target base (`git fetch origin main` for the usual base), then run:

   ```bash
   python3 scripts/hype-pr/pr.py inspect --repo OWNER/REPO \
     --output /tmp/hype-pr-inspect.json --assessment-template /tmp/hype-pr-assessment.json
   ```

   Use unique temporary filenames when multiple agents work concurrently. Inspect
   is read-only toward GitHub; it reads the three registered repositories at pinned
   commits. Fix new missing owners, invalid references, or missing criteria mappings
   and commit again. It reports existing debt separately. If source access fails,
   restore access; never replace unreadable source with empty content.

2. You are the reasoning agent. Read changed sources and relevant parents/affected
   nodes listed in the report at the recorded commits. Fill the assessment template:
   - `summary`: concrete purpose and effect of this change.
   - Each affected node: `disposition` (`change-required`, `satisfied`, `no-impact`,
     `unknown`), substantive `reason`, and issue/PR `followups` for unresolved impact.
     Include upward consistency and downstream requirements, design and validation.
   - Each unmapped watched path: classify `implementation`, `supporting`, or
     `editorial`, reference existing node IDs and explain the relationship.
     Implementation links require both a requirement and a test. New criteria
     themselves belong in the registry; do not disguise them as supporting edits.
   - `validation`: actual check, `pass` or justified `not-applicable`, and evidence.
     Do not report unrun tests as passing. A link/command is an agent attestation,
     not independently verified evidence of user or learning outcomes.

   Preserve the fingerprint generated by inspect. If the source changes, inspect
   again and reconsider the judgments; do not merely transplant a fingerprint.
   No additional model-provider key is needed: the coding agent performs reasoning.

   **Assessment rules.** `prepare` checks all of these and lists every failure with
   its JSON path (for example `validation[0].evidence: 14 chars, needs >= 20`). The
   template carries the same list under `_rules`; top-level `_` keys are ignored.
   - `summary`, every `reason` and every `evidence`: at least 20 characters.
   - `reviews`: exactly one entry per affected node in the report, no other IDs.
     `disposition` is one of `change-required`, `no-impact`, `satisfied`, `unknown`.
   - `unknown` and `change-required` need `followups`: a non-empty list of
     `https://github.com/<owner>/<repo>/issues/<n>` or `/pull/<n>` URLs in a
     registered repository.
   - `path_links`: exactly one entry per unmapped watched path. `kind` is one of
     `implementation`, `supporting`, `editorial`; `nodes` is a non-empty list of node
     IDs registered in the report; `implementation` needs a requirement and a test node.
   - `validation`: a non-empty list; each entry has a `check`, a `result` of `pass` or
     `not-applicable`, and `evidence`.

   A stale assessment or receipt names what moved (`head`, `base_tip`,
   `source_commits[<repo>]`, `tool_version`, branch or repository). Inspect again
   and reassess. Pass `--base` as a bare branch name (`main`, not `origin/main`);
   inspect fetches the base once when its remote tip is not in the checkout yet.

3. Bind the assessment to the current revisions:

   ```bash
   python3 scripts/hype-pr/pr.py prepare --repo OWNER/REPO \
     --assessment /tmp/hype-pr-assessment.json
   ```

   Prepare returns the receipt path inside this worktree's git metadata. Keep local
   reports and reasoning out of tracked/public files. Another commit, base movement,
   dependency revision, or policy/tool change invalidates preparation.

4. If the target repository commits `config/pr-body-contract.json` with
   `release_check.enforced: true`, write a `## Release check` section. Read both the
   linked issue body (the intent) and the code change, then write:

   ```markdown
   ## Release check
   How to verify: <where> → <what to click or run> → <expected result>
   Smoke: yes|no — <reason>
   Smoke check: <file under the contract's smoke_check_prefix, or #follow-up-issue>
   ```

   `How to verify` is the first line because the release manager reads that line.
   Answer `Smoke: yes` when the change adds a dependency on another repository or a
   server. `Smoke check` is required only for `yes`. When the linked issue answered
   "Smoke needed?" with yes and the PR says no, add
   `Smoke differs from issue: <reason>`. `create --apply` refuses a body that is
   missing any of these, keeps a placeholder, or has fewer than three verify parts.

   When the contract also sets `release_check.manager_check: true`, the section
   starts with `Release manager check: yes|no — <reason>`:
   - `yes` only when a user sees or meets changed behavior in the rc App (a screen,
     a reply, an install step). `How to verify` follows on the next line.
   - `no` otherwise, with the reason; `How to verify` is then not asked. Examples:
     release tooling only, CI only, vendored tooling only, docs only.
   - `Smoke` is answered either way. A hotfix ignores this line.

   If the contract on the default branch declares a `hotfix` lane, a PR whose
   `--base` starts with its `base_prefix` (for example `hotfix/v2026.1013.0`, cut
   from the last v tag) is a hotfix: `create` adds the `hotfix` label, refuses
   `--auto-merge`, and asks only for the Smoke lines (the release manager's
   checklist is skipped, smoke is not). Put several hotfixes from the same tag on
   the same `hotfix/<tag>` branch. The hotfix PR cannot close its issue, so bring
   the fix to the default branch in a second PR with `--forward-of <hotfix PR>`
   and a `Forward-port of #N` line; that PR gets `hotfix-forward`, a normal
   Release check, and closes the issue. `hotfix` on a PR into main is refused.

5. Push the prepared branch, then create through the guarded command:

   ```bash
   python3 scripts/hype-pr/pr.py create --repo OWNER/REPO --head BRANCH \
     --title 'feat(scope): 한글 요약' --body-file /tmp/pr-body.md --author LOGIN \
     --issue ISSUE_NUMBER --preparation RECEIPT_PATH --apply
   ```

   **Agent identity (local runs).** An agent session commits, pushes and creates as
   the `hypeproof-agent` GitHub App, not as the human whose machine it runs on.
   Prefix each of those commands with the canonical Harness wrapper and pass
   `--author 'hypeproof-agent[bot]'`:

   ```bash
   AGENT="$HYPEPROOF_HARNESS/scripts/agent-identity/with-agent-identity.sh"  # or ../hypeproof-harness/...
   "$AGENT" git commit ...
   "$AGENT" git push -u origin BRANCH
   "$AGENT" python3 scripts/hype-pr/pr.py create ... --author 'hypeproof-agent[bot]' --apply
   ```

   The human is then a real second person on the PR, and their approval satisfies
   the control-plane gate and review rules that exclude the author. A push after an
   approval makes that approval stale. If the wrapper cannot mint a token (no App
   key on this machine), stop and say so instead of falling back to the human's
   identity without being told to.

   The PR body must close that issue and no other issue. Omit `--apply` for a command
   preview. The apply path verifies that the target is an existing open same-repository
   issue rather than a PR or Epic, then recomputes source checks,
   verifies the remote head, derives risk from the actual diff and adds a fixed
   preparation summary to the PR body. Assessment prose is not published. Reviewer
   requests are disabled by default, and any catch-all CODEOWNERS requests created
   with the PR are removed before the command succeeds. If a draft is later marked
   ready, inspect and remove any catch-all request GitHub creates at that transition
   unless the user explicitly requested peer review. Add `--request-reviewers`
   only when the user explicitly asks for peer review on that PR. On stale preparation,
   repeat inspection/assessment; do not use direct `gh pr create` as a workaround.

In Work, run these same commands through `runWorkCommand` in the canonical
`scripts/hype-pr/work_host.js`. Use read-only host options for inspect/prepare;
enable create only for the authorized repository and exact branch. The host
rechecks live refs and connected author before creating the PR. A lost response
can leave a created PR: inspect GitHub before retrying; never replay automatically.
Keep source replies and assessments in private scratch directories, not commits.
Transport changes under development may be exercised on their own branch when
the user has authorized implementing this transport; this is not human approval.

PR creation is not merge authorization. Follow the user's existing authorization
and repository merge requirements. This is the standard agent workflow, not a new
GitHub required check or a guarantee against deliberate direct-CLI bypass. Human
adoption approval remains separate, and downstream changes may stay in linked work.
