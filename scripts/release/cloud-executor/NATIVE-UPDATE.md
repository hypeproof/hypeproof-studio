# Installed updater verification

`installed-runner.mjs` runs UPDATE through the installed product's command palette: check for updates, install, and confirm restart. It observes the restarted candidate executable and the existing synthetic Studio account, workspace and settings. It does not invoke an installer primitive as substitute acceptance.

Run the existing installed runner CLI on a disposable GitHub-hosted macOS or Windows desktop host with its normal signed candidate/N−1 manifests and package directories. The runner keeps every installation and profile under a new OS-temp `hps-installed-*` directory. It never attaches to or closes a user's existing Studio process. `native-capabilities.mjs [baseline-app-path]` provides a read-only prerequisite inventory without launching an app.

Additional environment inputs:

- `HPS_NATIVE_TEST_SEAT_FILE`: local JSON for an **already existing** synthetic Service account. Required fields are `kind: "synthetic-release-test-seat"`, `profileId: "synthetic-release-acceptance"`, `accountId`, `expectedEmail` ending in `.invalid`, `serviceBase`, `siteBase`, `approvalUrl`, and `bridgeKey` (at least 16 characters). `approvalUrl` must be a local HTTP 127.0.0.1 endpoint ending in `/internal/accounts/device/approve`. The harness approves only the device code displayed by the actual Studio account UI. It never provisions a customer, opens a cohort or injects a credential into app storage. Keep this file out of artifacts/source control.
- `HPS_NATIVE_EXPECTED_TEAM_ID`: actual expected Apple signing team. Both original baseline and candidate must pass normal `codesign` and `spctl` assessment. No quarantine, Gatekeeper, DNS or TLS bypass is applied.
- `HPS_NATIVE_EXPECTED_PUBLISHER_THUMBPRINT`: actual expected Windows Authenticode publisher certificate. Windows User and System packages remain separate. System installation uses genuine UAC; the observed product must run under a normal, unelevated user token after restart.

The original N−1 package must advertise `hypeproofReleaseVerification` schema `hps-native-verification-capability/1` with `loopbackPinnedFeed` and `isolatedRelaunch`. An older released package without this capability is **BLOCKED**. Rebuilding that package is not evidence of updating the original release. A future baseline release containing this feature is therefore necessary for this feed-based native acceptance path.

The feed is explicitly a local verification transport, not proof of a deployed customer update channel. The actual product updater fetches a raw-SHA256-pinned immutable manifest and the exact candidate package bytes over a temporary 127.0.0.1 HTTP port. Every request must be anonymous. Any invalid marker, ownership, feed, manifest or package hash fails closed without production fallback. The marker expires, requires the real isolated user-data directory and an executable inside the isolated install, and preserves isolated arguments through the product's normal Mac/Windows installer/relaunch scripts. Feed credentials, release credentials and model credentials are not forwarded.

Evidence includes exact before/after source and version, package digest, actual UI screenshots, normal platform signing assessment, owned process identity, actual existing account identity without a second approval, and retained workspace/settings hashes. Missing native host, baseline capability, signing identity, test seat, OS secure storage or interactive UAC is reported as NOT_RUN/BLOCKED, never PASS. No native installed acceptance was run on the developer's active Mac during this implementation.

Tests: `node --test scripts/release/test/native-update.test.mjs`; `node extensions/hypeproof-chat/test/update-verification.smoke.mjs`; the existing updater transport, installer and Windows wrapper smoke suites; extension typecheck/build. PowerShell execution and signed native UI acceptance require their real hosts. Windows package selection uses the installed `product.json.target` (`user` or `system`), as generated by [upstream VS Code's Windows packaging](https://github.com/microsoft/vscode/blob/main/build/gulpfile.vscode.win32.ts).
